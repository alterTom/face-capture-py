# 0.1.1 抓拍延迟修复

## 证据

用户截图显示两个动作均已通过，页面停留在“请选择清晰照片”阶段。读取本机已安装服务日志：2026-09-20 21:56:13.083 进入照片质量等待，21:56:36.437 才抓拍成功，间隔约 23.35 秒。另一次等待约 1.80 秒。旧日志没有逐项质量值，因此无法断言这次具体是哪项指标不达标。

代码确认，末动作已有 0.2 秒回正验证，随后重新要求所有拍照条件连续通过 0.6 秒，任意一帧失败就清零。浏览器还串行等待预览下载，并在返回 JPEG 前 await 清理 DELETE（最多额外 3 秒）。

## 实施

复用最后动作回正验证，符合质量的当前帧立即抓拍。保留全部原质量阈值、动作闭环和多人/失脸重置。质量不满足时给出具体原因并记录数值，避免一直显示笼统的选图提示。

预览请求与状态轮询并行，同一时间最多一份预览请求；结束时取消未完成预览，忽略迟到回调。清理在后台执行，不延迟照片交付，服务端仍有会话 TTL 兜底。

## 验证

新增回归测试复现旧问题：末动作完成帧不能立即抓拍、清晰度波动后合格帧仍等待、缺少具体提示、慢预览阻塞完成状态、慢清理阻塞图片返回。

- 全部 29 项 Python 测试和 2 项 SDK 测试通过，包含真实采集函数在最终回正帧直接编码、不再多读帧的回归测试。
- 0.1.1 打包程序离线模型自检通过。
- 浏览器运行最新页面，使用单独的模拟摄像头服务完成眨眼并成功显示 640×480 JPEG，控制台无错误。模拟画面明确标记 SIMULATED TEST FRAME。
- 独立复核未发现质量门槛绕过或取消竞态。

未使用真人重新完成端到端采集，实际延迟仍需用户摄像头复测；本次没有停止或替换用户已安装的旧版服务。
